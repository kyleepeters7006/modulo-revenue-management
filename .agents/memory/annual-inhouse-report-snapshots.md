---
name: Annual in-house report snapshots
description: Durable data and ownership rules for the Annual In-House Increase Plan report.
---

Annual reports are presentation snapshots of an already calculated in-house plan. They must never become a second solver or recalculate results while loading, printing, or exporting.

**Why:** Executive totals, occupancy-tier scenarios, charts, and PDF output must reconcile exactly to the decision the operator reviewed. Saving full resident records would also duplicate sensitive operational data unnecessarily.

**How to apply:** Only an explicit operator action to save/open Annual Report may upsert one latest report per tenant and exact calculation scope with a server timestamp; restoring cached plans or merely calculating must never silently overwrite that report. Also save resident details in a separate authenticated server snapshot, not in browser storage or the report payload. Restore detail snapshots only when their input fingerprint matches the current editor, normalize legacy `serviceLine`/current `sl` wrappers, and recalculate when no valid detail plan remains. Build the request from an explicit report-field allowlist (never spread the solver result), preserve tier cells, use measured tiers for totals, and persist six distribution counts—not resident or room arrays. When compacting an already compacted rollup with no resident rows, preserve its saved distributions instead of recomputing empty counts. Keep each service-line plan only once; tier-grid rows may omit embedded plan objects, so web and PDF renderers must read compact plan data from the report's top-level plans when restoring charts. Quarter snapshots retain conclusions used by the UI, not solver narratives or bridge rows. Every UI and PDF renderer that accepts restored plans must therefore treat compacted solver-only rates, explanations, and detail arrays as optional and render an explicit unavailable state. Enforce a client payload budget below the default parser limit, authenticate every operation, and keep daily health-care rates distinct from monthly senior-housing rates. In the executive YoY bridge, Plan Increase is the exact resident annual increase shown in the table, Total YoY is the projected plan-year average versus prior-year average, and Prior-period Increase is the residual so the first two add exactly to Total YoY. Combined revenue is Total YoY revenue growth: projected plan-year average minus prior-year average, times resident count and 12; occupancy-tier scenario revenue remains plan-only. The approved executive layout is a fixed two-page landscape worksheet: Combined + pricing-position charts on page 1, all three occupancy tiers on page 2, with 0.25-inch side and 0.75-inch top/bottom margins.

The report banner and combined total row must sum the same per-service-line annualized YoY revenue values; do not mix stored plan annual increases with the growth-bridge basis.

For division and portfolio campus rollups, choose one scoped automatic-run generation for the whole rollup. If a campus/service line is absent from that generation, leave that input unavailable and expose the incomplete state instead of silently substituting an older campus snapshot.

**Why:** Campus fan-out work can finish at different times, and independently choosing each campus's newest row creates totals with inconsistent calculation inputs.

**How to apply:** Carry the generation state through the saved tier-grid snapshot so the web report, PDF, and Excel audit workbook use the same warning and never imply that a partial rollup is complete.
